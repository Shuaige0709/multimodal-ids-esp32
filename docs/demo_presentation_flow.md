# 燕子守望：開發檢視用的既有日誌回放

正式競賽已改為 **5 張英文投影片＋現場攻擊**，請優先使用 [競賽手冊](../demo/competition/README.md)。本頁的回放只供開發檢視，不用於競賽 demo，也不代替實際攻擊。

## 先看新版網頁

新版只改電腦端網頁與回放工具，**不用重燒 ESP32**。建議先用現有日誌看效果，不需要接板子或啟動 Kali，也不會產生新實驗 CSV。

若原本網頁服務還占用 8080，先在其終端 Ctrl+C。在 Windows 專案目錄執行：

```powershell
.\scripts\start_demo_replay.ps1 -Scene Recovery
```

打開 `http://localhost:8080`。手機用腳本印出的 Phone 網址，與電腦同網路。頁面會一直標示「已錄製資料回放」，使用原始時間間隔，依真實 UART 日誌重新驅動同一套狀態判讀，沒有人工添加告警或恢復事件。

Recovery 約 125 秒，涵蓋已有的 Deauth／Disassoc 及恢復；結束後頁面保留結果並顯示「回放已結束」。Ctrl+C 關閉，再選下一段。回放不開 COM 埠、不送攻擊、不寫回原始檔案。

## 建議五分鐘版本

1. **20 秒：說明用途。**「這是一個放在 IoT 裝置上的無線安全監控器。看到攻擊會告警，部分攻擊會自動修復；如果設備斷線，也能看見重連和恢復。」指向 ESP32 與 OLED，說明偵測在板子上執行，網頁負責呈現。
2. **75 秒：單向 ARP，防護關閉。** 用下面的 ArpOff 回放，觀察告警及「路由器沒有回應」。只描述 gateway 測試，不說整個網際網路都斷了。
3. **75 秒：同類攻擊，防護開啟。** ArpOn 回放顯示「已鎖定可信任路由器」以及路由器持續回覆。說明本輪 ON 46/46、OFF 4/31 的區間觀測，避免把一次測試包裝成通用 100% 成功率。
4. **125 秒：斷線與恢復。** Recovery 回放，看大字的 Wi-Fi 斷線／重連狀態、持續增加的中斷時間，最後保留下來的實際恢復時長。說明這是恢復能力，不是阻擋成功。
5. **20 秒：收尾。**「我們已驗證單向 ARP 防護；雙向 ARP 和無線洪水仍有控制權與媒介限制。六類偵測、裝置狀態和修復結果在同一個介面觀察。」

三段回放加開場／收尾約五分半，視評審時間可只選 ArpOn＋Recovery，縮至約四分鐘。若只有兩分鐘，展示 ArpOn，搭配已完成的 [驗收結果](demo_acceptance_results_20261118.md) 說明恢復能力，不為縮短而加速或捏造事件。

## 可直接複製的回放命令

一次只開一段；換段先 Ctrl+C。這些命令全部使用現有檔案。

```powershell
.\scripts\start_demo_replay.ps1 -Scene ArpOff
```

```powershell
.\scripts\start_demo_replay.ps1 -Scene ArpOn
```

```powershell
.\scripts\start_demo_replay.ps1 -Scene Recovery
```

若評審問「那雙向攻擊呢？」可選既有失敗案例，不須新測試：

```powershell
.\scripts\start_demo_replay.ps1 -Scene ArpTwoWay
```

這段會呈現已執行防護、但路由器仍沒有回覆的情況。清楚區分「做了動作」與「真的恢復」，比不加區分地顯示成功更有說服力。

## 新介面的閱讀順序

- 左上：目前發現什麼，例如強制斷線攻擊、偽裝基地台；不是一串欄位代號。
- 右上：裝置還能否通訊。Wi-Fi 斷線用大字與底色顯示；重連時顯示本次中斷時間；恢復後留下上次中斷多久與恢復時間，不會八秒後完全消失。
- 自動防護：用「可信任路由器」「修復通知」「路由器回應」替代「映射」「GARP」等內部術語。
- 事件紀錄：實際告警與斷線事件。短暫已結束的無線告警仍沿用至少 1 秒的顯示篩選；ARP 單次身分事件保留，原始 CSV／JSON 不變。
- 技術資訊：預設收合；要回答工程問題才展開 USB 資料、IP、AP 限制、PMF 設定與測試累計。
- 中文／Eng：切換頁面標題、攻擊名稱、狀態、歷史紀錄及技術資訊，保留語言偏好；不改資料、模型或事件分類。

不預設顯示「安全／攻擊已阻擋」這種過度保證。沒有告警僅表示目前沒有告警，gateway 回覆僅代表路由器檢查可達。

## 現場與回放怎麼區分

目前的現場模式仍由 `start_demo_dashboard.ps1` 讀 USB，偵測與防護都在 ESP32；這次沒有變更板端判定。只有實際使用現場模式才需要 USB 與裝置。

回放模式使用同一份 UI 和狀態程式，資料來自舊日誌；不需要板子，頁面上方會標出來源與歷史時間，結束後凍結最後狀態並標示結束，不假裝仍在即時監控。不要同時用同一個 8080 埠啟動現場與回放。

不增加新錄製的備援就是保留這兩份 `.csv.log` 和專案程式。沒有原始日誌的組員須另取本機資料，git pull 不會自動取得未提交的實驗檔。

## 介面參考與採用理由

- [Uptime Kuma 官方專案](https://github.com/louislam/uptime-kuma)：參考「目前狀態」與「事件歷史」分開呈現的監控方式；沒有複製其程式碼或標誌。
- [GOV.UK 狀態標籤](https://design-system.service.gov.uk/components/tag/)：狀態要有明確文字，不只靠顏色，也不讓狀態標籤看起來像可操作按鈕。
- [GOV.UK 語言切換](https://design-system.service.gov.uk/components/language-navigation/)：切換時保留頁面資料、提供完整關鍵資訊的兩種語言。
- [GOV.UK 通知橫幅](https://design-system.service.gov.uk/components/notification-banner/)：避免重複橫幅；連線問題直接放在主區域，回放標示則常駐顯示資料模式。

這是監控工具，不是行銷頁；因此沒有加入見證、FAQ、宣傳口號或裝飾性進度動畫。
