# 2026-11-18 防護驗收結果與收案限制

## 結論

本輪防護驗收到此結束，不再新增錄製。既有資料支持「單向 ARP 攻擊下，本機修復與鎖定可維持到路由器的回覆」；雙向 ARP 尚未保住通訊。Deauth／Disassoc 已展示偵測與自動恢復，未建立攻擊期間阻擋成功的證據。Probe／Beacon／Twin 已有告警且這輪通訊持續，但沒有防護開關帶來額外改善的證據。

PMF 掃描顯示指定 2.4 GHz BSSID **目前未宣告 PMF 支援**；不進行 Required 模式與額外攻擊驗收。這不等於路由器硬體永遠不支援 PMF。

攻擊區間使用 CSV 中連續 `label=1` 的首末時間；第一個 ARP 區間依已執行腳本順序判為單向、第二個判為雙向，CSV 標籤本身都只寫 `ARP_SPOOF`。區間再對齊 UART 主控台接收時間，存在標籤與傳輸邊界誤差，因此不是封包級的精密延遲量測。

這是兩輪功能驗收，不是多次獨立重複、隨機化的防護效益實驗。ON／OFF 同時切換 ARP 修復與 AP 綁定，不能把所有差異歸因於單一元件。兩輪 PMF 都是 Optional，並非 PMF Disabled 對照。

## 各攻擊的結果

### 單向 ARP：本輪防護有效

- ON：`11:45:15.901225–11:46:07.715307`，504 個標註視窗，路由器回覆 **46 次、timeout 0 次**；停止後 30 秒回覆 26 次、timeout 0 次。
- OFF：`13:28:40.163861–13:29:31.978321`，503 個標註視窗，回覆 **4 次、timeout 27 次**；停止後 30 秒回覆 27 次、timeout 0 次。
- 兩輪該區間都沒有 Wi-Fi 斷線。差異在區域網路通訊，不是 station 關聯狀態。
- 可說「這次單向 ARP 測試中，啟用防護後維持路由器回覆」；不能推論為所有 ARP 攻擊的 100% 防護率，也不代表應用資料沒有被竊聽。

### 雙向 ARP：限量 GARP 尚未維持通訊

- ON：`11:46:39.560717–11:47:29.941335`，489 個標註視窗，回覆 **4 次、timeout 27 次**；攻擊區間記錄 2 次成功交給堆疊的 GARP，區間後 30 秒另 1 次，期間回覆 16 次、timeout 7 次。
- OFF：`13:30:03.825458–13:30:54.309371`，490 個標註視窗，回覆 **2 次、timeout 28 次**；停止後 30 秒回覆 26 次、timeout 0 次。
- ON 的本機鎖定沒有等同於回程恢復。路由器可能不採用廣播修復通知，也可能被持續投毒再覆寫；本輪沒有直接讀取路由器 ARP 表，不能把原因寫成已完全證實。
- 本機可控制自己的路由器紀錄；無法強制路由器接受修正。更可靠的雙向保護需要網路設備配合，這階段不追加工程或測試。

### Probe flood：偵測到，兩輪服務皆持續

- ON：315 個標註視窗中 300 個有最終告警，路由器回覆 **28 次、timeout 0 次**。
- OFF：317 個標註視窗中 302 個有最終告警，回覆 **29 次、timeout 0 次**。
- 兩輪均無區間內 Wi-Fi 斷線。可展示告警與通訊持續，不能宣稱防護擋掉了這些無線發射。

### Beacon flood：偵測到，兩輪服務皆持續

- ON：312 個標註視窗中 291 個有最終告警，回覆 **28 次、timeout 0 次**。
- OFF：312 個標註視窗中 289 個有最終告警，回覆 **29 次、timeout 0 次**。
- 兩輪均無區間內 Wi-Fi 斷線。單一 station 的程式無法收回已被占用的無線空中時間。

### Evil Twin：看到同名 AP，未驗證誘導連線防護

- ON：309 個標註視窗中 278 個有最終告警，回覆 **29 次、timeout 0 次**。
- OFF：313 個標註視窗中 289 個有最終告警，回覆 **29 次、timeout 0 次**。
- 可信任 BSSID 限制已加入，但腳本主要製造同名 AP 訊號，沒有充分挑戰重新選 AP 的行為，故無法從這兩場證明綁定的增益。BSSID 本身可偽造。
- 後續程式又補了最低 WPA2 安全等級，以拒絕 open／舊安全模式降級；該設定不是這兩輪的新增實測成果，不回溯套用成已驗證的效果。

### Deauth／Disassoc：偵測與自動恢復有效，阻擋未成立

- Deauth：ON 有 274／324 個告警視窗；OFF 有 264／315 個。兩輪都形成實際斷線事件。
- Disassoc：ON 有 255／297 個告警視窗；OFF 有 258／302 個。兩輪同樣斷線。
- dashboard 事件摘要：ON 的 Deauth 中斷 **43.5 秒**、Disassoc **38.8 秒**；OFF 分別 **32.7 秒、37.0 秒**。均記錄到 Wi-Fi 恢復。每段重試中的多個 reason code 不算成多次獨立攻擊。
- 這些時長包含攻擊與重連過程，不是純分類器延遲，也不等於「攻擊停止後等待這麼久」。ON 沒有展現較快恢復；不可宣稱 ARP／BSSID 防護能縮短這兩類中斷。
- 斷線時 ICMP worker 暫停，所以各區間只剩少數 Ping、timeout 0，不代表通訊正常。應以 Wi-Fi 斷線與恢復事件判讀。
- PMF Required 原本是最後候選，但 AP 未宣告支援，這輪不再驗證。保留功能說明，不宣稱已部署 PMF 防護。

## 用語與展示界線

- 「看到攻擊」：感測到攻擊相關訊號；不能直接代表設備受害。
- 「發出告警」：實際最終告警成立；不能等同攻擊被阻擋。
- 「已啟動防護」：本機規則或修復動作已執行；不能等同通訊恢復。
- 「通訊已恢復」：驗證得到路由器連續回覆；仍只涵蓋這條檢查路徑。
- 「Wi-Fi 已恢復」：重新取得連線／IP；不保證所有應用流量恢復。

現場建議主張：**「在 ESP32 上偵測六類情境，提供單向 ARP 自動修復，並呈現斷線與自動恢復過程。」** 不主張六類攻擊都已被阻擋。
